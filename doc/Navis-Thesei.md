# Navis-Thesei: 文档治理形式化理论

> **命名**: Navis (船) + Theseus (忒修斯) — 忒修斯之船悖论应用于文档治理。
> 文档如船, 每条信息是木板。船航行(项目演进)时, 木板该如何换?

---

## 1. 核心问题

文档随项目演进会积累信息。每条信息(木板)的状态会随情境变化而改变。问题: 何时留存? 何时清理? 何时补充?

**判据本质**: 木板留存的理由是**它在承重**, 不是它曾经在那里。

---

## 2. 形式化

### 2.1 基本集合

| 符号 | 含义 |
|---|---|
| `B = {b₁, b₂, ...}` | 木板集合(文档中的每条信息) |
| `S = {s₁, s₂, ...}` | 情境集合(读者会话 / 任务场景) |
| `S_h ⊂ S` | 历史情境 |
| `S_c = S \ S_h` | 当前情境 |
| `D = {d₁, d₂, ...}` | 需求集合(读者需要回答的问题) |

### 2.2 承重关系

```
R(b, s) ≡ 木板 b 在情境 s 中被引用或依赖
```

承重是情境相关的: 同一木板在不同情境下承重状态不同。

### 2.3 木板四分类

| 状态 | 定义 | 含义 |
|---|---|---|
| **承重 L** | `L(b) ≡ ∃s ∈ S_c: R(b, s)` | 当前情境仍引用此木板 |
| **冗余 Red** | `Red(b) ≡ ∃b' ≠ b: ∀s ∈ S, R(b', s) ⊇ R(b, s)` | 另一木板完全覆盖此木板信息 |
| **过期 Stale** | `Stale(b) ≡ (∃s' ∈ S_h: R(b, s')) ∧ (¬L(b))` | 历史承重, 当前不承重 |
| **缺失 Miss** | `Miss(d) ≡ ¬∃b ∈ B: R(b, s_d)` | 需求 d 无木板满足(作用于需求, 非木板) |

注: L/Red/Stale 作用于木板 b; Miss 作用于需求 d。

### 2.4 状态转移(情境驱动)

情境变化(`S_c` 演进)导致木板状态转移:

```
L → Stale:   S_c 变化使 R(b, s) 不再成立
¬Red → Red:  新木板 b'' 使 R(b'', s) ⊇ R(b, s)
¬Miss → Miss: 新需求 d 出现, 无木板满足
Stale → ∅:   归档后从主流程移除(非物理删除)
```

---

## 3. 治理原则

| 原则 | 形式化 | 含义 |
|---|---|---|
| **P1 留存** | `b 留存 ⟺ L(b) ∧ ¬Red(b)` | 承重且非冗余 |
| **P2 清理** | `b 清理 ⟺ Red(b) ∨ Stale(b)` | 冗余或过期 |
| **P3 补充** | `d 补充 ⟺ Miss(d)` | 存在未满足需求 |
| **P4 归档** | `Stale(b) → 归档(非删除)` | 保留可追溯, 不占主流程 |
| **P5 活性** | `定期重评估 S_c` | 情境变化导致状态转移, 需重新分类 |

**P4 关键**: 过期木板归档而非删除 — 历史信息可能在未来情境回归时重新承重。

---

## 4. 失效条件

每块承重木板应标注失效条件:

```
Form(b).failure ≡ 使 L(b) → ¬L(b) 的情境变化
```

即: 什么样的情境变化会让此木板从承重变为过期。

**示例**:
```
b = "Xvfb 恒无 GPU, 软件渲染定论"
failure(b) = {s | s.tech = Wayland ∨ s.tech = GPU-accelerated-Xvfb}
```

失效条件让维护者知道: 当情境变化触及失效条件时, 需重新评估此木板。

---

## 5. 分层管理

| 层 | 定义 | 特征 |
|---|---|---|
| **Core 核心层** | `Core(b) ≡ L(b) ∧ high_confidence` | 永久承重, 高置信度(源码级/多次实测) |
| **Aux 辅助层** | `Aux(b) ≡ L(b) ∧ medium_confidence` | 当前承重, 可能随情境变化 |
| **Ref 参考层** | `Ref(b) ≡ Red(b) ∨ Stale(b)` | 归档, 可追溯但不占主流程 |

分层让新会话知道: 先读 Core, 按需读 Aux, 必要时查 Ref。

---

## 6. 反熵增

### 6.1 熵定义

```
Entropy(B) = |{b : Red(b) ∨ Stale(b)}| + |{d : Miss(d)}|
```

熵 = 冗余木板数 + 过期木板数 + 未满足需求数

### 6.2 治理目标

```
Governance: lim(t→∞) dEntropy/dt ≤ 0
```

理想态: `∀b ∈ B: L(b) ∧ ¬Red(b) ∧ ¬Stale(b)`, `∀d: ¬Miss(d)`

**现实**: 理想态不可达(情境持续变化导致状态转移), 只能持续逼近。

### 6.3 关键洞察

> 抑制熵增的关键不是少写, 而是定期清理 + 分层管理 + 明确失效条件。

- **少写** ≠ 低熵: 不写承重木板会增加 Miss(d), 熵反而上升
- **多写** ≠ 高熵: 写承重且非冗余的木板, 熵不增
- **不清理** = 熵增: Stale/Red 木板积累, 文档变历史垃圾堆
- **只清理不补充** = 熵增: Miss(d) 增加, 文档失去指导价值

---

## 7. 实施流程

```
1. 盘点 B (现有木板清单)
2. 评估 S_c (当前情境)
3. 分类: ∀b ∈ B, 判定 L(b) / Red(b) / Stale(b)
4. 清理: Red(b) → 删除; Stale(b) → 归档
5. 补充: ∀d ∈ D, Miss(d) → 新建木板
6. 标注: ∀b ∈ B with L(b), 标注 failure(b)
7. 分层: Core / Aux / Ref
8. 定期重复 (情境变化时)
```

---

## 8. 适用范围

- 软件工程交接文档(HANDOFF)
- API 文档 / 设计文档
- 经验库 / 教训库
- 任何"信息随情境变化而价值改变"的文档体系

---

## 9. 与传统文档治理的对比

| 维度 | 传统 | Navis-Thesei |
|---|---|---|
| 留存判据 | "曾经有用" | "当前承重"(L(b)) |
| 清理判据 | "看起来过时" | 形式化(Red ∨ Stale) |
| 缺失识别 | 被动(踩坑才发现) | 主动(Miss(d)) |
| 过期处理 | 删除 | 归档(P4, 保留可追溯) |
| 维护节奏 | 按需(出问题才改) | 定期(P5, 情境变化时) |
| 信息密度 | 追求"永远精简" | 追求"每条都承重" |

---

## 10. 局限性

1. **承重关系 R(b, s) 的判定依赖人工**: 无自动化方法判断"木板在情境中是否被引用"
2. **情境集合 S 难以穷举**: 未来情境不可预测, 失效条件只能覆盖已知变化
3. **冗余判定有模糊性**: "完全覆盖"(∀s, R(b',s) ⊇ R(b,s)) 在实践中难以严格判定
4. **归档成本**: Ref 层仍需维护, 否则归档变遗忘

## 11. 理论修正 (2026-08-20 实证后)

实证攻击测试案例后发现原理论的 3 处不严谨, 修正如下:

### 11.1 "部分覆盖" 概念 (修正 Red 判定)

原 Red(b) 要求"完全覆盖"(∀s, R(b',s) ⊇ R(b,s)), 实践中罕见。更常见的是"部分覆盖":

```
PartialRed(b, b') ≡ ∃s ∈ S: R(b', s) ⊇ R(b, s) ∧ ∃s' ∈ S: ¬(R(b', s') ⊇ R(b, s'))
```

即 b' 覆盖 b 的部分情境, 但不全部。PartialRed 的木板**不能直接清理**(仍有独有承重部分), 但可标记为"可部分合并"。

**实证**: HANDOFF.md 七、已知漏洞 V1 (Destroy 与帧泵竞态) 与经验 42 (FramePump 契约) 是 PartialRed 关系 — 经验 42 覆盖了"泵必须先 Stop"契约, 但未覆盖"Stop 与 UpdateFrame 交错的窗口期"盲区。

### 11.2 "经验" vs "应用实例" 区分 (修正 Stale 判定)

原 Stale(b) 判定木板本身过期, 但实践中需区分:
- **经验本身** (如经验 43 BootLock 死锁根因): 仍被代码引用 → L(b)
- **经验的应用实例** (如 Create 竞态探针): 经验 43 修复后不再可复现 → Stale(实例)

修正: Stale 应可作用于"木板的应用实例", 而非仅木板本身。

```
StaleInstance(b, i) ≡ (∃s' ∈ S_h: R_i(b, s')) ∧ (¬∃s ∈ S_c: R_i(b, s))
```

其中 i 是木板 b 的某个应用实例 (如某个探针、某段测试代码)。

### 11.3 归档命名约定 (修正 P4 实施)

P4 "归档(非删除)" 缺乏具体实施方式。补充命名约定:

```
归档文件: <name>.<YYYYMMDD>.achieved.<ext>
归档段落: 章节标题加 " — 已闭环 (YYYY-MM-DD)"
```

**实证**: 临时测试报告归档为 `<name>.<YYYYMMDD>.achieved.<ext>` (如 attack-report.20260820.achieved.md); HANDOFF.md 章节标题加 " — 已闭环 (YYYY-MM-DD)" (如 3.0)。

## 12. 实证案例 (HANDOFF.md 七、已知漏洞, 2026-08-20)

攻击性测试 (临时报告已归档, 漏洞信息沉淀于 HANDOFF.md "七、已知漏洞") 是 Navis-Thesei 理论的首次实证:

| 漏洞 | HANDOFF 状态 | 理论分类 | 治理动作 |
|---|---|---|---|
| 重复 Destroy UAF | 已修复 | L → 经验 | P1 留存 → 经验 45 |
| 快速重建卡死 | 未修复 | Miss(d) | P3 补充 → 七、已知漏洞 V3 |
| 高频 resize 风暴卡死 | 未修复 | Miss(d) | P3 补充 → 七、已知漏洞 V2 |
| Destroy 与帧泵竞态 | 经验 42 部分覆盖 | PartialRed + 部分 Miss | P3 补充 → 七、已知漏洞 V1 |
| Create 竞态 (已修复) | 经验 43 已修复 | StaleInstance(43, 探针) | P4 归档 → 探针删除 |
| Start/Stop 竞态 | 经验 42 覆盖 | Red(b) | 不补充 |

**理论有效性**: 四分类 + PartialRed + StaleInstance 能对所有漏洞做明确分类, P1/P3/P4 指导了具体治理动作 (1 条经验留存 + 3 条已知漏洞 + 1 个探针归档删除)。

**理论局限性验证**: R(b,s) 的人工判定 (漏洞 V1 的 PartialRed 需人工分析"经验 42 契约的盲区") 和 S 的不可穷举性 (重复 Destroy 之前未预测到此情境) 均在实证中确认。
